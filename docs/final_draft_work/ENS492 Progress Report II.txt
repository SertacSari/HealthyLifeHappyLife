Summary
Project Description
HealthyLifeHappyLife is a mobile application designed to support users in developing healthier nutrition and fitness habits through meal logging, workout tracking, profile-based goals, dashboard summaries, and rule-based motivational support.
Gap in Existing Solutions
Many existing nutrition and fitness applications are overly complex, visually overwhelming, or restrict important features behind paid subscriptions. There is a need for a simpler, more accessible, and motivating alternative for everyday users.
Motivation
The project is motivated by the need to reduce cognitive overload in health tracking and to make habit formation easier to maintain through a clear interface, structured goals, and supportive features.

2. SCIENTIFIC / TECHNICAL DEVELOPMENTS
Since the previous report, the project has progressed from design into a working implementation stage. The conceptual system, preliminary UI design, and architecture decisions prepared during ENS 491 were used to build a runnable Month 1 MVP. The current version includes a Node.js backend, a React Native mobile interface, protected authentication flow, profile management, meal and workout logging, and a basic dashboard summary. 
The implementation is organized around a client-server structure. The mobile application communicates with a REST-style backend API that provides authentication, profile, meals, workouts, and dashboard-summary endpoints. For rapid MVP delivery, the current persistence layer uses a lightweight JSON-based data store, while migration to PostgreSQL remains planned for the later phase.

Design Decisions and Detailed Design
Because the project must be completed within limited time by a three-person team, the main design decision was to begin with a simple MVP instead of implementing all planned features at once. The team therefore prioritized the end-to-end core flow: authentication, profile-goal management, meal logging, workout logging, and dashboard aggregation. 
At the detailed-design level, the system was separated into mobile, backend, and documentation layers. The backend was structured around dedicated endpoints for authentication, profile, meals, workouts, and dashboard summary. The mobile application was organized into tab-based sections so that the user can move clearly between dashboard, meals, workouts, and profile screens. Validation, protected routes, and user-scoped data access were included to keep the MVP technically coherent. Manual checks and smoke-test style verification were used to confirm that the core flows run successfully. The current MVP therefore serves as a practical engineering baseline for the remaining development work.

Commercialization Potential / Market Search
Commercialization is not a primary goal of this project; however, a brief market review was carried out to evaluate the relevance of the application domain. Recent industry analyses indicate that the broader fitness and nutrition app market continues to grow, suggesting sustained demand for mobile tools that support habit tracking, guidance, and motivation.
The market review shows that the global fitness apps market was estimated at USD 12.12 billion in 2025, while the global diet and nutrition apps market was valued at USD 2.14 billion in 2024. In addition, industry reporting indicates that global Health and Fitness app downloads reached 3.6 billion in 2024, reflecting strong user adoption of mobile wellness tools. These observations suggest that a simple and accessible tracking application remains relevant in practice, even though this project is being developed as an academic prototype rather than a product for immediate commercial launch.
No formal patent search or Freedom-to-Use analysis has been carried out at this stage. Based on the current prototype, no immediate FTU issue has been identified because the system relies on standard development technologies and original project-specific application logic rather than proprietary medical workflows.


3. ENCOUNTERED PROBLEMS
The project goals remain relevant, but several implementation-level adjustments were necessary to keep the work feasible. In addition, although the project was initially proposed by four members during ENS 491, the ENS 492 implementation phase has been continued by three active members. The original design included broader social features, richer recommendation support, and a more advanced persistence strategy. During implementation, the team decided to prioritize a stable Month 1 MVP before extending the feature set.
One important change concerned data storage. The initial plan mentioned PostgreSQL as the main database technology, but for faster MVP delivery the current version uses a lightweight JSON-based persistence layer. This decision reduced setup complexity and enabled quicker end-to-end integration, but it also means that database hardening and migration work still remain before the final stage.
Another difficulty involved schedule pressure and coordination. Because of other course responsibilities, development moved more slowly than originally intended. In addition, local environment and API-host handling created practical testing issues during simulator and device runs. As a corrective measure, the team clarified work distribution, focused first on the critical user journey, and used smoke tests and manual verification to confirm core functionality.
These changes affected the implementation by narrowing the immediate scope to the most essential user flows. However, this corrective approach helped the project move from a design-only state into a functioning MVP, which is a stronger basis for completing the final report successfully.
